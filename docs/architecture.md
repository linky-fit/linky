# Architecture

Architectural decisions and behavioral constraints for Linky. Keep this file up to date: document new architectural decisions here (not in `AGENTS.md`) in the same commit as the change.

## Local error tracker (`tools/nostr-error-tracker/`)

- Standalone local Vite dashboard for the existing kind-24134 payment telemetry inbox. It only displays `status: error`; reporting producers and payloads are unchanged. Groups use error code, method, and phase, plus message for unknown errors; occurrences retain all received metadata and the original JSON, including older reports missing environment fields.
- Dashboard filters use the URL query as their source of truth (`q`, repeated `version`, `platform`, `runtime`, `host`, `mint`, `period`, `from`, `to`, `solved`, `sort`). Default values are omitted; unrelated parameters and the hash are preserved. Browser history restores selections, including before login; search text replaces the current entry. Relative periods are recalculated at login, refresh, and history navigation. Custom date boundaries keep the browser's local-time semantics.
- Seed-only authentication uses Linky's shared SLIP-39 derivation. The normalized 20-word phrase is stored under `linky.errorTracker.seed` in localStorage and restored on reload. Signing out removes it and reloads the page to terminate Evolu workers, since Evolu 7.4.1 does not implement disposal. Nostr extension and nsec-only login are unsupported because they cannot derive the same Evolu owner.
- A dedicated `errorTracker` owner uses BIP-85 path `m/83696968'/39'/0'/24'/7'/0'`, separate from the app's existing owner lanes. The tracker opens an owner-specific Evolu database and defaults to `wss://evolu.linky.fit`; `VITE_EVOLU_SERVER_URLS` overrides it. Only append-only resolution records sync: SHA-256 of the existing issue grouping key, solve time in milliseconds, and a report timestamp cutoff. Raw reports and the recovery seed are never written to this table. Evolu encrypts changes before relay transport; local SQLite data remains on the device after sign-out.
- Resolution cutoffs are the later of the solve time rounded down to seconds and the latest known occurrence. The greatest cutoff wins across devices, independent of delivery order. An issue is solved unless an occurrence has a strictly later `createdAtSec`; such issues reopen as reoccurred. Late older reports do not reopen issues, and reports in the same second cannot be ordered more precisely. Status derives from all loaded occurrences, regardless of version/date filters; recurrence is reconstructed from the synced resolution and Nostr history. Saves finish after the local database commits and sync when connected. Solved issues are hidden by default; Show solved includes all statuses.
- This admin tool uses `nostr-tools` directly for local decryption and paginated archive queries, outside the app's linkstr runtime. It never publishes Nostr events. It verifies outer/seal signatures, rumor hashes and sender/recipient binding, discovers collector relay lists, and deduplicates retries by report ID. Queries walk backwards through available history with overlapping timestamps; cancellations, timeouts and unresolved timestamp limits are explicit. Relay retention and undisclosed per-query caps can still make history incomplete.

## Site (`apps/site/`)

- Public website lives in `apps/site/` and is intended for a separate deploy on `linky.fit`; the product PWA stays in `apps/web-app/` for `app.linky.fit`
- `apps/site/` must stay a non-PWA marketing site: no web manifest, no service worker registration, and install prompts should only come from `app.linky.fit`
- `apps/site/cashu/` is a separate MPA entry for direct `/cashu` loads; Cashu token privacy should prefer hash fragments (`/cashu/#cashu...`) because query strings are sent to the server on the initial request
- Landing page is static copy plus product screenshots (`apps/site/public/*.png`); the floating CTA offers Web app, Google Play, Android APK, and Zapstore targets, defaults to Web app, and prefers Google Play when the browser is on an Android phone
- On Android, the Google Play CTA navigates to an intent targeting `com.android.vending`, falling back to the web app if Play Store cannot open. The fallback avoids the Play listing because Chrome can route that back to the unavailable Play Store. Other platforms use the HTTPS listing directly
- Landing page and `/cashu` share the top-right language selector (`SiteHeaderMenu`) and the footer (`SiteFooter`); locale and display currency persist under `linky.lang` / `linky.display_currency.v1` (`sitePreferences.ts`). `/cashu` cycles the display currency by tapping the token amount, with `₿` still meaning sats rather than whole bitcoin
- `/cashu` is a consumer of `@linky/linkshu` and `@linky/linkstr`. `CashuPage` renders the UI, `useCashuPage` owns its state and handlers, and `cashu/wallet.ts` composes package operations. Linkshu owns LNURL parsing and invoice validation, amount fallback, mint loading/proof state, icon metadata/overrides and fiat-rate decoding/fetching. LNURL functions accept an optional HTTP fallback supplied by each app: the web/native adapter retains its hosted proxy, while the site uses the address-only proxy below. Existing web-app LNURL tests exercise that adapter.
- Site wallets persist seed, token rows, counters and the exact pending melt quote per normalized token under `linky.site.wallet.<hash>`. A Web Lock serializes operations across tabs. Storage must succeed before spending. `MeltDraft.quoteId` reuses the saved quote, verifies its invoice, and `Melt.status` checks settlement without paying again. Reload recovery waits on PENDING, reports PAID to the original address, or restores deterministic outputs and retries only after UNPAID. Change is recovered through `Restore`; reserved rows are released only after a terminal mint answer. `MintInfo.isFakeLightning` identifies known test URLs and published metadata advertising FakeWallet or automatically paid invoices. The site rejects these mints before fetching a Lightning invoice; the smoke build enables `VITE_ALLOW_TEST_MINT=1` only for known test URLs.
- Site telemetry uses linkstr's durable `Outbox` through `runLinkstr`. The old queue key remains a Schema-validated staging buffer for events captured before enqueue; legacy entries migrate there without retaining a second retry engine. A Web Lock serializes workers across tabs; linkstr owns retries and recipient relay acknowledgements. Change forwarding uses `Chat.sendToken` with an ephemeral identity, and failed forwarding keeps a redeemable token visible. Relay defaults, analytics recipient, error classification and the `devicePlatform`/`appRuntime` detection are shared with the web app: linkstr's `detectTelemetryEnvironment` is the single implementation and takes browser facts (user agent, touch points, standalone display mode, `navigator.standalone`, and the native shell platform when the host knows it) as plain input, so both apps read their own globals and feed them in — the site passes `nativePlatform: null`, the web app passes its Capacitor target.
- `/cashu` reaches LNURL-pay endpoints directly first and falls back to the same-origin `/api/lnurlp` helper only for CORS-blocked providers; that helper takes a lightning address (plus optional `amount`/`comment`), performs both LNURL hops itself against public https hosts, and returns no CORS headers, so it cannot be used as a general fetch proxy
- All outbound HTTP from `apps/site/api/` goes through `api/_safeFetch.ts`. Every hop — the LNURL well-known endpoint, the callback it returns, the npub.cash forwards, and any redirect target — must be `https:` on a plain public hostname, is resolved with `dns.lookup({ all: true })` and rejected if any address is loopback, private, link-local, CGNAT, multicast, IPv4-mapped, or otherwise outside public unicast space (`isPublicAddress`), and then connects through an undici `Agent` whose `connect.lookup` returns exactly the validated addresses, so TLS SNI and `Host` keep the hostname while a DNS rebind between check and connect cannot redirect the socket. Redirects are followed manually (at most 3, each re-validated), every hop has a 12 s timeout, and response bodies are capped at 64 KiB
- `/cashu` token launch now prefers the native `cashu://receive?token=...` deep link, falls back to installed PWA handling via `web+cashu://receive?token=...`, and only then falls back to the browser `https://app.linky.fit/#wallet?cashu=...` import route
- Vercel rewrites `/.well-known/lnurlp/:user` and `/.well-known/nostr.json` into `apps/site/api/` serverless handlers so apex `linky.fit` can expose LNURL/NIP-05 while forwarding to `NPUBCASH_BASE_URL` (default `https://npub.linky.fit`); LNURL responses rewrite the returned callback back to the apex host
- The `/cashu` entry page can ingest a token from manual paste, query string, or preferably URL hash, inspect the token client-side, present `Vyzvednout v Linky` / primary Linky-open CTA first, reveal QR-copy plus Lightning-address redeem flow behind a secondary `Další možnosti` toggle, and redeem to a Lightning address; redeem sends the maximum LN-address amount the mint+LNURL flow allows, queues anonymous payment telemetry to the same collector/feed used by the app, and forwards any leftover token value as a private Nostr gift wrap to the configured collector `npub` from a one-time sender identity instead of returning change

## Local dev environment

- All external service endpoints are env-overridable with hardcoded production fallbacks: `VITE_NOSTR_RELAYS`, `VITE_EVOLU_SERVER_URLS` (comma-separated), `VITE_MAIN_MINT_URL`, `VITE_PUSH_SERVER_URL`, `VITE_NPUB_CASH_DISABLED` (declared in `apps/web-app/src/vite-env.d.ts`)
- Vite mode selects the environment: `development` mode loads the checked-in `apps/web-app/.env.development` pointing at the `docker-compose.dev.yml` stack (Nostr relay :7777, Evolu relay :4001, Nutshell FakeWallet mint :3338, push :8787); `prod-services` mode (`bun run dev:prod`, port 5175) loads no overrides and hits production. Distinct ports keep localStorage/OPFS/service-worker state origin-isolated between the two modes, so a local-dev identity can never bleed into a prod session
- Relay and Evolu server lists are user-persisted settings; env vars only change the *defaults* for a fresh origin
- The local Evolu relay image (`docker/evolu-relay/`) pins `@evolu/nodejs` + `@evolu/common` versions that must stay protocol-compatible with the web app's `@evolu/common` — verify the pairing via the upstream `apps/relay/CHANGELOG.md` before bumping either side (the official `evoluhq/relay` image is not used because it hardcodes a 1MB-per-owner quota)
- `isTestMintUrl` treats any `localhost`/`127.0.0.1` mint as a test mint (skips Lightning fee probes, grouped separately in the mints UI); the FakeWallet mint auto-settles invoices after ~3s and exposes deterministic failure/delay knobs via `FAKEWALLET_*` env vars in `docker-compose.dev.yml` — there is no working stochastic-failure option in Nutshell
- Integration and E2E payments use a second Nutshell FakeWallet mint on :3339, with a distinct key and database (`cashu-mint-target`, profiles `integration` and `e2e`). Invoice recipients use this target so source melts take the external-payment path instead of racing the source mint auto-paying its own quote. Autoswap tests assert source proofs are spent and target proofs can be redeemed; Lightning settlement is still simulated
- npub.cash-compatible flows are skipped entirely in local dev (`VITE_NPUB_CASH_DISABLED=true` guards the info/claim/mint-sync entry points via `isNpubCashDisabled()`); running npubcash-server locally is issue #219, a real Lightning backend for the local mint is issue #220
- Playwright web tests use the `local-stack` project against the Docker stack, with the app served from the `web-app` compose service (profile `e2e`, port 5176) as a **production build**. This exercises production chunks and effect timing. Compose owns the server. PR and release CI run this suite and the site redemption/recovery suite, which builds the site on :5180 against the same local mints and relay.
- Local-stack proxy-payment, migration, boot-recovery, and app-shell parity tests block service workers because Playwright cannot intercept requests a service worker makes. Chat recovery and password-save tests keep the service worker enabled. Chat recovery exercises offline reload; signup verifies the real iframe response

## Linkstr protocol package (`packages/linkstr/`)

- `@linky/linkstr` is the single home for Linky's app-level Nostr protocol: every operation the app publishes and every inbound action it expects will be defined here as Effect `Schema` types, with raw nostr events confined to per-vertical codec modules and `internal/`. Consumers (web app, service worker, push service) are meant to import typed drafts/receipts/inbox facts, never `nostr-tools`
- Environment-agnostic by rule: no React, no Evolu, no `window`/`localStorage`. Capabilities enter via Effect services — `LinkstrIdentity` (pubkey + secret key), `NostrTransport` (per-relay publish outcomes), `RelayPolicy` (one source of truth for read and write relay sets); the durable `Outbox` owns invisible delivery retries
- Outbox delivery has two independent FIFO lanes: chat and reactions share the foreground lane; payment telemetry uses the background lane. Each lane retries with its own backoff, so a rejected report cannot delay a message. Enqueue wakes only its lane; the browser `online` event wakes both. Jobs keep the same storage format and share the existing terminal-results stream.
- Delivery semantics are explicit: NIP-17 sends wrap one rumor twice (self copy + recipient copy) and success requires the *recipient* copy to be accepted by ≥1 relay; "only my self copy landed" is the typed `RecipientNotReached` error, never a silent success
- Every wrap vertical sends through one skeleton (`internal/wrapSend.ts`: `sendToPeer` for the two-copy NIP-17 send, `sendToRecipient` for single-copy rumors such as payment notices and telemetry) and every receipt names the rumor it delivered `rumorId` — the same field on `ChatMessageReceipt`, `ReactionReceipt`, `BankOfferReceipt`, `EnqueueReceipt`, …, so consumers never dispatch on receipt class to find the id. Receipts are `Schema.TaggedClass`es (`_tag` = the class name), so the persisted `OutboxReceipt` union decodes by tag, never by structure or member order — `ReactionReceipt` and `ChatMessageReceipt` have identical fields. Single-copy sends fail with `WrapNotDelivered`. `PersistedOutboxJob` (`outbox/domain.ts`) still decodes two older generations of stored jobs: untagged receipts take their tag from the job's operation, and receipts keyed by a per-vertical id (`messageId`, `reactionId`, `telemetryId`) are additionally renamed to `rumorId`, so an upgrade never drops a stored job list
- Errors use `Schema.TaggedError` (serializable by policy, so outbox rows can persist failures); inbound wraps decode to a tagged union of app-level facts (`ReactionAdded`, `OwnReactionConfirmed`, …) or a `WrapDropped` with a typed reason — consumers `Match.exhaustive` over the union
- Inbound gift wraps are authenticated in the package (nostr-tools `unwrapEvent` verifies nothing): seal signature must verify, rumor author must equal the seal author, rumor id must be the rumor's hash. Publishing goes through `ensureRelay().publish()` per relay because `SimplePool.publish` resolves connection failures as strings — treating a resolved promise as acceptance reports unreachable relays as delivered (the legacy web-app publish path had this bug until it was replaced by linkstr)
- The reactions vertical (kind 7 + kind 5 retraction inside kind-1059 gift wraps) is the reference implementation; chat messages, payment notices, and bank offers share the same shapes. Chat content, reaction sends, and payment telemetry enqueue durable `Outbox` jobs keyed to app refs (telemetry through `enqueueTelemetry`, which skips the precomputed-rumor path because each attempt mints a fresh ephemeral author); one global results listener idempotently marks rows sent after terminal delivery, while reaction retractions stay direct. All wrap *receiving* runs through `WrapInbox`, mounted via the linkstr-react handler/inbox atoms in the app's single `useLinkstrInboxSync` dispatcher — the legacy raw-pool inbox pipeline is gone. The plain-event verticals (profiles/status, relay lists, mute list) are fully migrated: the app no longer signs or queries those kinds through the shared pool
- The seen-receipts vertical (kind 24136 inside gift wraps, `["linky","seen_receipt"]`-tagged) carries a read-receipt **window cursor** "(sinceSec, seenUpToSec]" — content holds `seenUpToSec`, a `since` tag holds the sender's receipts-enabled baseline, so per-message receipt state never exists on the wire. Receipts send direct (no `Outbox`): every receipt supersedes all previous ones, so a lost send self-heals at the next trigger, and outbox retry semantics would republish a stale cursor. They carry no push marker (silent). The codec mirrors the reactions own-echo split: `OwnSeenReceiptConfirmed` (with `to` = the non-author p-tag) for self copies, `SeenReceiptReceived` for peer receipts, strict decode otherwise (`invalid-seen-receipt`)
- `WrapInbox` owns the app's single kind-1059 subscription. `open({ since })` is a scoped resource: it starts one resubscribe loop per read relay (a dead relay never stalls the others; `NostrTransport.subscribe` runs one honest per-relay subscription that resolves with the relay's close reason) and returns a queue-backed **single-consumer** `Stream` of typed inbox facts. A plain queue was chosen over a broadcast PubSub because a PubSub drops events published before consumers attach, and backfill starts the moment the machine opens; the one consumer (the react boundary) fans out to verticals. Closing the scope tears down every relay subscription and ends the stream
- `PushInbox` is the identity-free kind-1059 sibling used by `apps/push`: `watchPushInbox` composes it over `NostrTransport` without a `LinkstrIdentity`; one reconnecting subscription per relay uses only `{ kinds: [1059], since }`, and the push codec enforces `["linky","push"]` client-side because relay-side multi-letter tag filters are nonstandard and strfry rejects them. It emits signature-verified outer-wrap facts with recipient/relay-hint routing and per-relay `backfill`/`live` delivery. Linkstr FIFO-dedupes authenticated live emissions across relays but re-emits every backfill copy; `apps/push` suppresses backfill without recording it, so a later live copy is still delivered. The service's SQLite ledger records only wraps it attempted to deliver for restart-safe dedupe. `apps/push` never decrypts wraps or imports `nostr-tools`; Linkstr's push codec imports `nostr-tools` to verify outer signatures
- Rumor routing has exactly one dispatch point, in `WrapInbox`: kinds 14/15 go through the chat codec, 7/5 through reactions, 24133 through payment notices, 24135 through bank offers, 24136 through seen receipts; every other kind is a `WrapDropped("unsupported-kind")` until its vertical exists (payment telemetry 24134 remains). Wraps are deduped across relays by wrap id in a FIFO-bounded set (4096 ids); only *authenticated* wraps enter the set, so a tampered copy from one relay cannot suppress the honest copy from another, and an eviction can only re-emit an old wrap, which is safe because inbox facts are idempotent by rumor id
- Cursor contract: the machine tracks the max authenticated wrap `created_at`, clamped to the current time so a sender-controlled future timestamp cannot make restarts skip events. The cursor is loaded from and checkpointed to the `InboxCursorStore` port (platform code supplies the layer, like `OutboxStore`; defaults to in-memory), with `open({ since })` only seeding a first session whose store is empty; every (re)subscription widens the cursor by two days because NIP-59 randomizes wrap timestamps up to two days into the past, so restarts replay a bounded window that dedupe and idempotency absorb. Checkpointing eagerly on every advance (not after consumers handle the event) is deliberate: the margin re-widens `since` past everything the current session could still deliver, so a crash mid-handling never loses events the after-handling timing would have saved. For this reason the transport's `SimplePool` runs with `enableReconnect: false`: nostr-tools' transparent reconnect re-fires subscriptions with `since = lastEmitted + 1`, stripping the margin, which in practice silently dropped roughly half of newly arriving gift wraps for the rest of the session after any socket drop (network switch, mobile background, or a relay that ignores the `limit: 0` keepalive REQ — nostr-rs-relay does — where the ping cycle kills the connection every ~50s). A dropped socket now hard-closes its subscriptions, and the verticals' resubscribe loops re-fire them with correct margin-widened filters
- The plain-event surface (non-gift-wrapped kinds) mirrors the wrap verticals: `Profiles` (kind 0 + kind 30315 `d=general` status), `RelayLists` (kind 10002 + 10050, published as one operation with per-event receipts), `MuteList` (kind 10000). Publishes share one helper (`deliverPlainEvent`): sign with the configured identity, publish to every write relay, succeed on ≥1 acceptance, else the typed `NoRelayAcceptedEvent` (plain sibling of the wrap-shaped delivery errors). Kind-0 content decodes tolerantly (unknown fields ignored, non-string fields dropped, `display_name`/`displayName` both accepted; publishing emits standard wire names only) and status content is an opaque string — Linky's conventions stay app-side
- `identity/codec.ts` holds the pure nip19/key codecs (`decodeNsec`, `decodeNpub`, `parsePubkey`, `derivePubkey`, `identityFromNsec`, nprofile helpers) returning the branded `Pubkey`/`NostrSecretKey` types. This makes the "consumers never import nostr-tools" rule literal for the web app: `nostr-tools` is a devDependency there, used only by tests that deliberately build fixtures with an independent implementation. Note the codecs enforce the `Pubkey` on-curve check at parse time, so off-curve 64-hex input is rejected where the app previously accepted it until a send failed deep in derivation
- `httpAuth` is a pure-codec vertical with no transport: signed nostr events used as HTTP credentials, never published to relays. `makeBlossomUploadAuthHeader` (kind 24242, base64url `Nostr` header for Blossom uploads), `makePushOwnershipProof` plus `verifyPushOwnershipProof` (the shared kind-27235 challenge-proof wire contract for client and push server), and `makeNip98AuthHeader` (kind 27235, wire-identical to nostr-tools' `nip98.getToken` incl. payload hashing and padded base64 — pinned by a compat test). Encoders take an explicit `now: UnixSeconds` like every codec; consumers no longer finalize or verify these events through `nostr-tools` directly
- `ProfileWatch` is the plain sibling of `WrapInbox`: one `{ kinds: [0, 30315], authors }` subscription per read relay for a fixed pubkey set, events signature-verified (a plain event's own signature is its only authentication), newest-wins per (pubkey, kind) in-session so a lagging relay can't downgrade, 30315 tracked only in the `d=general` slot with NIP-40 expiration enforced. It emits `ProfileUpdated`/`StatusUpdated` facts and persists nothing — consumers compare `updatedAt` with their own cache. Changing the watched set closes the scope and re-invokes `watch` (the react boundary does this on `watchedProfilesAtom` change, without rebuilding the runtime)
- One-shot fetches (`fetchProfile`, `fetchOwnRelayLists`, `fetchWrapEvent`) use `NostrTransport.fetch(relay, filter)`, which collects stored events until EOSE — or a bounded timeout (5s), returning what arrived — then closes; per-relay like `subscribe`, fanned out over read relays and failing only when every relay was unreachable (`AllRelaysUnreachable`). Plain-event fetches validate and sort the raw fan-out before their codecs see it; gift-wrap fetches use the same authenticated unwrap and rumor routing as `WrapInbox`, and may union caller-provided relay hints with configured read relays. The inspector sees fetch traffic through `PlainOperationSucceeded` (despite the legacy name, its event ids can identify plain events or wraps) and `WireFetched`
- The React boundary lives in `@linky/linkstr-react` (`packages/linkstr-react/`, built on effect-atom): a config atom holds identity + relay sets + a transport seam, a runtime atom rebuilds (finalizing the previous scope and relay pool) whenever that config changes, and each vertical exposes fn atoms returning typed Exits — `LinkstrNotConfigured` while logged out. The package re-exports the effect-atom react surface (`useAtomSet` etc.), so app code drives the atoms directly and never depends on effect-atom itself. `@linky/linkstr` itself stays React-free. Service assembly has one home in linkstr: `linkstrServices(config)` layers every vertical over the base services with the transport taken as an already-decorated layer — the react runtime wraps it with the inspector/relay-health taps, and the headless entry `runLinkstr(config, effect)` runs one effect against a fresh composition (no decorators, `writeRelays` defaulting to none) and closes the relay pool when the run ends; `fetchWrapEvent` takes an optional `timeout` for callers on an external deadline, resolving null instead of failing
- Observability is a first-class optional service: `Inspector` is a diagnostics bus (sync `emit`, single-consumer sliding stream) that services reach through `Effect.serviceOption` (`Inspector.orNoop`), so not providing it costs nothing. Emission points are the same chokepoints all verticals share — each vertical's send service emits `OperationSucceeded`/`OperationFailed` (full params + both wrap deliveries), `inspectTransport` decorates any `NostrTransport` layer with wire events (`WirePublished`, `WireSubscribed`, `WireEventReceived`, …), and `WrapInbox` emits `InboxRouted`/`InboxWrapDeduped`, so unknown rumor kinds surface with their kind number even before a vertical exists. Inspector rows use structurally validated, open namespaced channels such as `nostr.operation` and `nostr.wire`, so future domains do not require schema changes. Correlating ids live in the open-label `links` map, while non-correlating location/environment metadata lives in `context`; operation and wire events currently correlate by wrap id / rumor id / client id. The react boundary turns it on via `LinkstrConfig.inspector` and exposes `inspectorHandlerAtom` + `inspectorEventsAtom`; the web app uses one emission gate (dev or either Advanced inspector toggle) and fans rows into independent sinks: the per-tab in-memory viewer when its toggle is on, the Vite HTTP collector only in dev, and an optional on-device IndexedDB log. The persistent sink is lazy-loaded, batches writes, and prunes on startup and every write to a rolling 24-hour/~25 MiB window; disabling it clears its unsynced, unencrypted device-local buffer, while download serializes the same collected-row NDJSON accepted by inspector import. Production builds have no remote reporting path
- The dev inspector collector rejects foreign Origin headers and cross-site Fetch Metadata before reading or mutating rows. Same-origin browser and headerless CLI requests remain supported; Vite validates hosts first. The collector restricts its directory to mode 0700 and its current per-port NDJSON file to 0600, including existing files. The dev file still retains the session without a size cap
- Relay connection status is traffic-derived, never probed: `RelayHealth` is an always-on production service (unlike the optional `Inspector`) holding a per-relay `RelayHealthState` snapshot — `connecting`/`connected`/`unreachable`, last close/error `detail`, `lastSeenAt`, `lastErrorAt`, and the `lastPublish` outcome (write relays may carry no subscription, so their freshest signal is the last publish, shown with its timestamp). Its feeder is `observeTransport`, a transport decorator structurally identical to `inspectTransport`; both are transparent taps composed in the react runtime, and `RelayHealth.live` is always merged in. Transitions fold over real traffic: subscribe → connecting; EOSE, a received event, a fetch result, or an accepted publish → connected (an accepted publish promotes state because it proves the relay served us; a failed publish only records `lastPublish` + `lastErrorAt`, since the transport cannot distinguish a policy rejection from a connection failure); a subscription ending or `RelayUnreachable` → unreachable with the reason, which the verticals' resubscribe loops flip back to connecting (exponential backoff with jitter from a 5s base, capped at 12×, reset once a subscription stays up past 6× the base — `internal/resubscribe.ts`). To make EOSE visible, `NostrTransport.subscribe` takes an optional `{ onEose }`. Snapshot writes are deduped by value equality, so event floods cost at most one write per relay per second. The react boundary exposes `relayHealthAtom`; the relay settings UI consumes it, replacing the app's former raw-WebSocket probing in `useRelayDomain`

## Linkshu cashu package (`packages/linkshu/`)

- `@linky/linkshu` is Linky's cashu wallet as a platform-independent Effect package, cloning the linkstr blueprint: ports as `Context.Tag` services, verticals as `Effect.Service` classes with `.Default` layers, one composition entry (`linkshuServices`), a Promise-facing headless runner (`runLinkshu`), and an optional `Inspector` diagnostics bus reached via `orNoop`. Raw cashu-ts types never cross the public boundary; token text is the currency of the API. No dependency edge to `@linky/linkstr` in either direction. The interface contract (#286) fixed the full surface first and implementation landed slice by slice; no stub is left
- Platform ports with exported in-memory defaults: `KeyValueStore` — durable string storage with two lease-lock primitives (`tryAcquireLease`/`releaseLease`), because deterministic counters must advance under cross-context mutual exclusion (tabs, service worker, CLI); acquisition retries and timeouts are package semantics (`internal/lease.ts` — `withKeyLease`, ttl/acquire-timeout 15s, a 50 ms `Effect.retry` schedule on a null lease, release always runs via `acquireUseRelease`). `ProofStore` — the wallet inventory, one row per proof (`available` / `held` / `handedOut` / `externalized` / `spent`), ids a pure function of the secret so every device converges; `OperationStore` — every durable link between inputs and outputs (`melt`, `topup`, `autoswap`, `send`, `receive`), ids derived from the operation key (`operationKeyOf`: kind + token text for transfers, kind + mint + quote id for quotes), so an insert of a known key is an upsert. Both are dumb: every state decision is package logic. `CashuSeed` — raw 64-byte BIP-39 seed; platforms never derive anything
- Mint/wallet management owns the package's single wallet-instance cache: an internal `WalletInstances` service (never exported) holds one in-flight-deduped cashu-ts wallet promise per mint+unit per runtime — the same mint/unit is never loaded twice concurrently, failures evict only their own entry. This replaces the web app's several uncoordinated per-hook caches. Wallet loading preserves the app's pinned keyset-verification fallback: on a keyset-verification-shaped error only, fetch info/keysets/keys manually (keys for every same-unit hex keyset, active and inactive), prime the wallet via `loadMintFromCache`, and bind the lowest-fee active hex keyset of the unit. Mint failures are classified at the boundary into transient `MintUnreachable` (network, timeout, 5xx — retry later, never mark state) vs definitive `MintRejected`; raw errors never cross
- Proofs are the inventory (#345): `Tokens.balances` sums `available` proofs (`spendable` = largest single-mint sum); spending offers only NUT-07-confirmed `UNSPENT` available proofs and marks `SPENT` ones `spent` — a terminal state, never a delete, because restore and re-ingest dedup against it. `Send` stores its outputs as `handedOut` under a `send` operation (status `issued` | `pending`), change as `available`, consumed inputs as `spent`; `Melt` holds its inputs as `held` under a `melt` operation until the mint answers (PAID → change `available`, inputs `spent`, status `paid`; UNPAID → inputs `available`, `unpaid`; rejected → `failed`; unresolved → `PaymentPending`, settled by `Melt.resumePending`). `held` with a null `operationId` means "held by an operation this wallet has no record of" (migrated `reserved` rows); `Validation.checkAll` releases such proofs once the mint reports them `UNSPENT`. `Receive` records a `receive` transfer (`pending` → `done`, or `failed` carrying the serialized error so a re-paste retries); dedup is by transfer text and by stored proof secret. `Tokens` owns the transfer transitions platforms are not allowed to write themselves: `markIssued` (pending → issued), `markExternalized`, `forget` (close as `done`: a delivered messenger send, a dismissed failed receive), and `returnToWallet` — a handed-out send is re-received through the shared accept flow so the encoding somebody else may hold dies at the mint (its proofs → `spent`, status `returned`; `TokenAlreadySpent` means the recipient claimed it → `done`), a pending or failed receive is retried in place. `Validation.checkIssued` marks handed-out proofs the mint reports spent and closes claimed sends as `done`; `checkTransfer` checks one send's proofs or one received text. Only availability and terminal mint state are persisted; `pending`/`unknown` answers stay in the `inspectProofStates` snapshot
- Cross-vertical helpers live in `src/internal/` and are never exported: `quoteRecordStore(ctx, codec, ttl)` is the one durable quote record store behind melt's `meltRecords`, topup's `topupRecords`, and autoswap's `autoswapRecords`: a typed view over the `pending` operations of one kind in the `OperationStore` (`create`, `withCounter`, `settle(status, error?)`, `read`, `readAll`, deadline = the mint-stated expiry else `createdAt` + 24h). The deterministic output slot (`counter`) is on the synced operation, so any device can resume any quote. `readAll` first carries the previous releases' key-value records (`linkshu.pendingMelt.*`, `linkshu.pendingTopup.*`, `linkshu.pendingAutoswapClaim.*`) over into operations and deletes those keys; `quoteClaim` takes that store rather than persist/clear callbacks; `pollUntil` is the bounded `Schedule`-driven poll (attempts × interval, first answer accepted by `settled`) behind Melt's pending-settlement wait and Autoswap's claim wait; `quotes.ts` owns `decodeMintQuote` (a mint quote must carry an id and an invoice) and `emitQuoteState`; `time.ts` (`nowSeconds`), `units.ts` (`sat`), `operations.ts` (`inspectOperationWith`, `redactReceipt` = the receipt minus `tokenText`) and `errorMessage.ts` hold the rest

- Deterministic output collision recovery covers signed-output codes `11003`/`11005`, pending-output `11004`, and CDK `11008` (`Duplicate outputs`, also used for existing stored promises). Signed and duplicate errors walk NUT-09 from the colliding counter to the end of the derivation tree (`DERIVATION_GAP_LIMIT` = 1000 unsigned positions end a walk; `Restore` scans with the same limit, because reserved 64-slot output blocks of failed attempts leave gaps a 300-slot limit stopped at, parking the counter on signed slots) and retry just past the last signed slot; missing signatures use the operation's fixed counter bump. - The send vertical runs through linkshu `Send` plus the `Tokens` lifecycle. Emitting a QR/share token (`emitCashuToken`) sends `produceAs: "issued"`; issued transfers are claim-watched through `Validation.checkIssued` (one composition-level wrapper with a shared in-flight promise serves the list-page mount check, the manual button, the token-page 10s poll, and the 60s background tick) and closed as `done` by the package once NUT-07 reports their proofs spent. Sends are exact-amount: linkshu swaps out exactly the requested amount (fee comes out of the change, stored `available` before the consumed inputs are marked `spent`) or fails `InsufficientFunds` — the old degrade-the-amount retry ladder is deleted for sends (LN-address melt still uses it). - The melt vertical (paying a bolt11 invoice or an LN address from the cashu balance) runs through linkshu `Melt`: quote, fee-inclusive swap, melt, and persistence are package-owned — NUT-08 change and any post-swap remainder come back as `available` proofs before the receipt resolves, and a failed melt leaves the balance intact. A melt the mint has not settled (still `PENDING` past the poll budget, or a lost response the quote check cannot resolve) fails with `PaymentPending`: the inputs stay `held` under the synced `melt` operation (written before the melt request leaves, so any device can finish it), and `Melt.resumePending` — wired like the topup and autoswap resumers, once when the runtime comes up and again on the browser `online` event — settles it on the mint's own answer: `PAID` reclaims change via NUT-09 over the recorded blank slots, `UNPAID` returns the inputs to balance, `PENDING` or no answer keeps both. Validation never touches proofs held by a known operation. The app records such a payment as a `pending` transaction carrying `meltQuoteId` in its details and flips it to paid (fee, amount) or failed when the resumer reports the outcome. LN address resolution (LNURL-pay) stays app-side in `lnurlPay.ts` — it is Lightning plumbing, not cashu. So does the amount-degrade retry ladder (`buildPaymentAmountAttempts`): it re-fetches the LNURL invoice at lower amounts when the requested amount plus fees exceeds the mint balance, which is UX policy over an external amount the app controls, not something a fixed-invoice melt can do; because linkshu failure semantics guarantee no balance change, retries need no recovery bookkeeping. `describeTaggedCashuError` renders `InsufficientFunds` with its `need X, have Y` amounts so the ladder can size the next attempt from the typed error. - The topup vertical (Lightning receive) runs through linkshu `Topup`: quote creation, the settlement poll, minting under the deterministic counter lock (including NUT-09 reclaim of an already-`ISSUED` quote), and the durable pending record are package-owned. The composition root keeps one long-lived Effect `Scope` next to the `ManagedRuntime` so topup polling fibers survive React unmounts and route changes and die only when the runtime is disposed; `useTopupFlow` drives the UI (invoice + QR with an embedded cashu payment request, paid overlay, payment-history event) off `StartCashuTopup`/`ResumePendingCashuTopups` handles. `resumePending` runs once when the runtime comes up and again on the browser `online` event (linkshu's poll gives up after a run of unreachable-mint failures; re-resuming re-attaches the persisted quotes — duplicate fibers are safe because claims are lease-locked and reclaim dedupes by proof secrets). Pending quotes are retired **only on the mint's own answer** — a quote the mint confirms UNPAID after its expiry (or the 24h fallback deadline for quotes without one) — replacing the old 24-hour local-clock prune, which could drop a quote that was paid while the device was offline. The old app-side topup machinery (`useTopupInvoiceQuoteEffects`, `topupQuoteStorage`, the claim-poll effect, `linky.local.pendingTopupQuote.v1.*` / `linky.topup.claimed.v1.*` storage) is deleted; legacy pending quotes from pre-cutover versions are not migrated. NUT-20 locked quotes carry a `locked` flag on the pending record and are minted with the `QuoteLockingKey` the caller passes to `adopt`/`resumePending` (never persisted or emitted); in the app that key is the nostr secret, derived in `useLinkshuComposition`

## Compatibility and audit decisions

- Existing browser storage names are upgrade contracts. Keep `linky_use_btc_symbol`, `linky_debug_evolu_sql`, `linky_nostr_profile_v2:`, `linky_nostr_status_v2:`, `linky_nostr_avatar_cache_v1`, `linky-push-debug-v1`, `linky-push-secrets-v1`, and `linky-push-contact-names-v1`. New names use `linky.`. Renaming these requires a migration across page/service-worker versions; changing a prefix alone can lose preferences or disconnect push credentials.
- Review historical migration removal for **26.10.1**, the earliest eligible release. Removal requires evidence that every supported upgrade source has completed the migration, or an enforced bridge upgrade with recovery coverage for offline devices returning from older releases. A release date or absence of reports is insufficient; until that evidence exists, retain the code and release-gating tests. This covers `linkshuStorageMigration`, `legacyAcceptedTokenDrain`, their call sites and tests, `MESSAGE_MIGRATION_VERSION`, `linky.contacts_owner_migrated_v1`, and `.migratedToEvolu.v2`. Remove each reader, flag, and fixture together only after proving the replacement preserves counters, pending claims, contacts, messages, and payment history.
- `wipeLinkshuSeedBoundState` remains part of every seed replacement/logout. Only its legacy migration prologue is eligible for removal. `autoWipeOnWasmOom.v1` limits retries of runtime OOM recovery, so it has no historical-migration expiry; changing that recovery policy requires separate storage-loss analysis.
- Inbound `messageId`, `reactionId`, `noticeId`, and `snapshotId` remain domain-specific names, all typed `RumorId`. They distinguish an observed fact from its `target` or retracted `reactionIds`. Outbound receipts use the uniform `rumorId` so the generic outbox can consume them. Tagged receipts already removed the old union-order hazard; retain legacy receipt decoding under the upgrade gate above.
- Keep the per-workspace eslint/prettier entry files and the empty shared Prettier config. Workspace commands resolve their own isolated Bun tool dependencies; centralizing requires root dependencies and changes configuration discovery. The small forwarding files keep workspace checks independently runnable.
- Keep the 64 KiB response cap and 12 s per-hop timeout in `safeFetch`. The endpoints exchange LNURL/NIP-05 JSON and invoices, not media. Redirect validation and the three-redirect bound remain mandatory. Change the limits only with a failing supported-provider fixture and the SSRF/oversize tests passing.
- Keep the outbox online-wake race, uptime-sensitive resubscribe delay, and top-up consecutive-failure counter. Their state resets differ from a simple retry schedule. Refactoring them must preserve interruption, successful-UNPAID reset, and pending paid-quote recovery tests.
- Keep the boot-stage console diagnostics because they run before the inspector loads. `bootDiagnostics.ts` also retains the current and previous boot attempts in per-tab session storage and lets every boot-error screen download a redacted JSON report; it omits URL queries and hashes because those can contain payment tokens or keys. Bootstrap deliberately renders the app without a root Suspense boundary: Evolu's `useQuery` suspends on every newly rendered query (owner-lane rotations included), and a boundary above the app would replace the mounted tree with a fallback and tear down its effects. Instead a `loadQuery` probe against `ownerMeta` records `await-initial-local-data` until the local database answers, then `await-render-commit` until the first commit. A `SqliteError` reported before the first commit reloads the page up to three times with a growing pause (`linky.boot.evolu_open_reload.v1`): after a reload the new database worker can start while the previous page's worker still holds its OPFS access handles for seconds, and the SAH pool does not retry. A further failure renders the boot-error screen. A caught React render error must stop the HTML-shell watchdog so the shell cannot overwrite the original error and component stack. The Buffer base64url polyfill is required by installed `@evolu/common` 7.4.1: `Type.js` selects `globalThis.Buffer.from(...).toString("base64url")` and `Buffer.from(..., "base64url")`, which `buffer` 6 does not implement. Recheck this path when upgrading either dependency.
- Service-worker push parsing and compact/long private-attachment parsing retain their compatibility behavior. A Schema replacement must preserve per-field optional recovery, both stored attachment shapes, and file-validation bounds. Raw localStorage remains confined to the migration and KeyValueStore adapter because storage defects must abort migration before its done flag or reach the Effect caller.
- Keep typed inspector construction without repeated validation for already-validated internal facts; wire and stored input still decode at their boundaries. Keep the wallet keyset-fallback warnings and push console logger until their diagnostics have an equivalent observable destination. Startup and service logging need explicit exceptions before adopting `no-console`. The identity adapter's nullable API intentionally maps failed derivation to the app's existing invalid-key flow; package callers retain typed Effect errors.
- Keep generated Android Gradle files tracked and the Java 17 patch until a clean Capacitor sync/build proves a replacement covers every plugin. A `MainActivity` split and Gradle override are separate native changes. Upload/download GitHub Action major versions are independent. App-wide result unions, naming changes, and React Compiler adoption also remain separate changes; they need consumer migration or measured render behavior, not a mechanical audit rewrite.

- Bolt11 preview parsing lives in linkshu as pure exports (`getLightningInvoicePreview`, `parseBolt11AmountMsat`, `getLightningInvoiceDescriptionHashHex`), shared by payment previews and LNURL checks. The existing bech32 parser and permissive partial-preview behavior are preserved; previews do not validate invoice signatures. The web app imports these helpers and `LightningInvoicePreview` from the package.

## Linkshu CLI wallet (`apps/linkshu-cli/`)

- `@linky/linkshu-cli` is the package's first consumer and its platform-independence proof: a terminal wallet running under plain Bun with no browser, React, or Evolu, driving the package through `runLinkshu`. It lives in `apps/` rather than `packages/` because nothing imports it — it is a runnable binary, like `apps/push`
- All three ports are implemented from files, and are written to be read as reference examples for the next platform. Durability lives in one module (`jsonFile.ts`) that both stores share: `modify` is the only writer, holding an exclusive lock (`open(…, "wx")`) across a re-read and an atomic temp-file `rename`, so readers never see a torn file and no writer can clobber another's update. Lock files older than 30s are treated as belonging to a dead process and broken. Contents that exist but do not decode raise rather than resetting the wallet, because a silent reset is indistinguishable from losing every token
- The token file is a JSON array of the port's own `StoredTokenRow` schema — no adapter mapping to drift from, unlike the app's Evolu adapter. The key-value file holds values and leases together, so acquiring a lease and writing under it take the same lock
- Seed resolution: `$LINKSHU_SEED` (hex), else `<data-dir>/seed.hex`, else a freshly generated seed written mode `0600`. Restoring a wiped data directory means passing the old seed back through the environment
- `--verbose` provides an `Inspector` layer whose `emit` writes one stderr line per event; stdout stays the command's result. The local-stack nginx server accepts its POST through an internal GET redirect so it returns the same empty HTML with HTTP 200 and never starts another app instance. The local-stack signup test exercises this real response; browser password-manager prompts still depend on browser heuristics.
- Cashu deterministic wallet seed is derived from the SLIP-39 secret using **BIP-85** at path `m/83696968'/39'/0'/24'/0'` (24-word mnemonic)
- Web app seed/identity helpers in `src/utils/slip39Nostr.ts` are app-level adapters that delegate SLIP-39/BIP-85 derivation to `@linky/identity`. `@linky/identity` depends on `@linky/linkstr` for the nostr key layer — `IdentityProvider` returns linkstr's `NostrSecretKey`/`Pubkey` brands and nsec/npub encoding uses linkstr's codecs; identity owns only derivation (SLIP-39, BIP-32/85, owner lanes) and has no direct `nostr-tools` dependency
- Seed derivation is a cross-app compatibility contract with Payky (`finitoapp/payky`): the same SLIP-39 share must recover the same master secret in both apps, and the cashu path `m/83696968'/39'/0'/24'/0'` must yield the same wallet. A shared vector table is pinned in `packages/identity/src/crossAppDerivation.test.ts` here and mirrored in Payky's `src/core/modules/shared/cross-app-derivation.test.ts`; intentional derivation changes must update both copies in the same way
- Own profile uses a dedicated `#profile/edit` route for editing; the top-left profile avatar modal remains for viewing QR/profile share info and its edit action now opens that standalone page instead of inline modal editing, and `#profile/claim-lightning` lets users check availability and price for a custom `@linky.fit` lightning address, pay the quote in-app, publish the chosen `lud16`, and re-activate the currently paid hosted alias later with one tap; the profile editor hides the default `Restore` button while such a paid alias exists
- Hosted npub.cash-compatible claim/info/mint sync always targets `https://npub.linky.fit`, independent of the `lud16` the profile publishes: every identity keeps a `<npub>@linky.fit` address on Linky's own server, so that origin is the only one that can answer for it. Upstream npub.cash retired its v1 API on 2026-08-07 (the v1 paths now return the SPA shell with status 200), so deriving the origin from the lightning-address domain left every user on another wallet's address polling a dead host
- Payments to `<npub>@npub.cash` are collected too, on the same poll and equally independent of the profile `lud16`. Upstream's v2 API holds no proofs: `GET /api/v2/wallet/quotes` (NIP-98 signed on the bare path; the query is not part of the signed url) lists the mint quotes it created for the address and which are paid, and the wallet mints them itself through linkshu `Topup.adopt`. `utils/npubCashUpstreamQuotes.ts` owns the listing, its parse, and the per-identity cursor/ledger (`linky.local.npubCashUpstreamQuotes.v1.*`): the cursor trails the newest settled `paidAt` by a 10-minute lookback (the server filters `paid_at > since`), the ledger holds the quote ids inside that window, and the cursor only advances when the listing was read to its end. A quote the mint already issued (minted by another client, e.g. npub.cash's own wallet) or definitively rejects is settled in the ledger; transient failures are retried next sweep. Proofs land on whatever mint upstream chose for the user (minibits by default) and are not auto-swapped to the main mint
- If the hosted mint update fails, Linky must not persist the new local main-mint choice as if it succeeded
- **LNURL-auth (LUD-04) signer.** Linky signs third-party logins; it is never a way to log into Linky, because an external wallet cannot supply the seed the Nostr identity and the Evolu owner lanes are derived from. `packages/identity/src/lnurlAuth.ts` derives the per-domain linking key from the **active Nostr secret key**, not from the SLIP-39 master secret as LUD-05 prescribes: `hashingKey = HMAC-SHA256(nostrSecretKey, "linky/lnurl-auth/hashing-key/v1")`, then `linkingKey = HMAC-SHA256(hashingKey, <lowercase host>)`, re-derived under a `/<n>` suffix in the vanishingly unlikely case the result falls outside the secp256k1 range. Pasted-nsec logins therefore get the same feature as seed logins, at the price of interoperability with other wallets — which costs nothing, since a linking key is only ever compared against itself. The consequence users can observe: switching the active Nostr identity switches the account every LNURL-auth site sees, exactly as switching identities does everywhere else in the app
- On web, the `nsec` private key is still mirrored under `linky.nostr_nsec`; native shells are expected to provide secure secret storage via the platform bridge and secrets must never be logged or exposed

### Evolu persistence and owner lanes

- Persisted contact, message, reaction, and transaction rows use query-inferred Evolu types exported from `evolu.ts`. `ContactRowLike` derives its display fields from those types and permits partial, unbranded fields for unsaved Nostr peers; mutation boundaries still validate branded IDs and text. Evolu creation dates are ISO strings, not numeric timestamps.
- Transaction history transforms live in `app/lib/transactionHistory.ts`. Nullable amount and fee columns stay null when absent (a NULL means "not recorded", e.g. `buildTransactionInsertPayload` omits a zero fee), and the transactions page renders them as absent — no amount text, no fee row, no expandable card for fee alone — never as `0 sat`; incomplete synced rows are skipped until required fields arrive. Indexed dictionaries can have missing keys even when TypeScript declares `Record<string, string>`, so their empty-value fallbacks remain.

- Runtime contact/transaction ID validation lives in `src/evoluIds.ts`, which does not initialize the database. `evolu.ts` re-exports these IDs for existing consumers; lightweight hooks import the schemas directly. Contact import, editing, and owner migration share the text-field constructors in `app/lib/contactFields.ts`.

- **Evolu** for all persistent data - local-first SQLite with sync. Schema in `src/evolu.ts`
- Before Evolu initializes its transports, a one-time installation migration adds and enables `wss://evolu.linky.fit`. It preserves custom servers, the removed-defaults flag, and other disabled servers; `linky.evoluServers.linkyRelayAdded.v1` is recorded only after the active settings contain Linky. Later removal or disabling is respected. Builds with `VITE_EVOLU_SERVER_URLS` skip the migration so local and test stacks stay isolated. The migration is silent in the UI and emits `evolu.linkyRelayMigrated` to the inspector.
- Web startup probes OPFS before creating Evolu. When the probe rejects (notably Safari Private Browsing, where OPFS is unavailable) or stalls past 3s, boot pauses and shows a consent prompt instead of silently degrading; only an explicit "Continue with temporary session" switches to Evolu's in-memory SQLite driver, while a stalled probe that recovers before the click dismisses the prompt and boots persistently. The same explicit recovery is offered if initial Evolu queries remain suspended until the boot watchdog fires, which covers a storage worker or IndexedDB transaction wedged after the OPFS probe succeeded. Consent is remembered per tab in `sessionStorage` (`linky.in_memory_session.v1`) so same-tab reloads (account restore, PWA auto-update) don't re-prompt. In-memory sessions still sync through the configured Evolu transports, so relay-backed data keeps loading. Both boot watchdogs (the bootstrap stuck-stage error and the index.html shell recovery reload) pause via `linky-boot-decision-pending`/`-resolved` events while the prompt awaits a decision
- Nostr chat persistence is Evolu-backed (`nostrMessage` + `nostrReaction` tables) and uses deterministic `messages-n` owner lanes for seed logins (derived from SLIP-39/BIP-85 path family `m/83696968'/39'/0'/24'/4'/<index>'`); legacy `linky.local.nostrMessages.v1.<ownerId>` data is imported once per owner via `linky.messages_evolu_migrated_v1:<ownerId>`
- For seed logins, contacts writes are routed through deterministic Evolu `contacts-n` owner lanes (derived from SLIP-39/BIP-85 path family `m/83696968'/39'/0'/24'/2'/<index>'`); the shared `ownerMeta` lane stores separate per-scope pointer rows such as `contacts-<n>`, `cashu-<n>`, `messages-<n>`, and `transactions-<n>`, and contact reads aggregate all visible `contacts-n` lanes up to the active index so old contacts stay visible without copy-forward
- For seed logins, cashu writes (`cashuProof`, `cashuOperation`, and the legacy `cashuToken` table) are routed through deterministic Evolu `cashu-n` owner lanes (derived from SLIP-39/BIP-85 path family `m/83696968'/39'/0'/24'/3'/<index>'`), with the active lane index mirrored in `ownerMeta` as `cashu-<n>`; cashu reads aggregate visible `cashu-n` lanes up to the active index so previously seen tokens remain dedupe-visible without copy-forward, and new writes no longer mirror into a contacts-aligned legacy lane
- For seed logins, active Nostr identity state is also mirrored into a dedicated deterministic Evolu `identity` owner lane (derived from `m/83696968'/39'/0'/24'/6'/0'`); the row stores the active `nsec`, `npub`, identity `source` (`derived` vs `custom`), and optional `switchedAtSec` cutoff used to ignore older incoming events after a custom override
- For seed logins, transaction writes/reads are routed through deterministic Evolu `transactions-n` owner lanes (derived from SLIP-39/BIP-85 path family `m/83696968'/39'/0'/24'/5'/<index>'`)
- AppShell subscribes Evolu sync for active seed lanes (`contacts-n`, `cashu-n`, `messages-n`, `transactions-n`, `identity`, and `ownerMeta`) via `useOwner`, so owner pointers/data converge across tabs/devices
- Contacts and cashu owner lanes auto-rotate independently on mutation-count thresholds (currently contacts `220`, cashu `170` over `cashuToken` + `cashuProof` + `cashuOperation` mutations — one row per proof means the cashu lane rotates more often than it did with token rows; the threshold is kept and revisited with real numbers) and enforce a 1-minute per-type cooldown; contacts and cashu both stay pointer-only without copy-forward, and new cashu writes stay on the active cashu lane only
- Messages owner lanes auto-rotate at `160` mutations with a pointer-only switch (no message copy), and message/reaction reads aggregate all visible `messages-n` owners up to the active index while writes stay on the newest owner
- Transactions owner lanes auto-rotate at `220` mutations with a pointer-only switch (no transaction copy), and transaction/history reads aggregate all visible `transactions-n` owners up to the active index while writes stay on the newest owner
- Auto-rotation counts historical mutations in `evolu_history`, using the synced `ownerMeta` rotation cutoff when present and the lane's full history otherwise. Lane zero and legacy lanes without snapshots therefore include updates and consumed/deleted rows, even when their live row count stays small. Thresholds count mutations, not bytes; a large token can still exceed a relay's byte quota before the threshold.
- Recovery of an empty cashu lane without a snapshot runs only for the initial stored index after the ownerMeta bootstrap grace period. Observing a snapshot or changing the active index ends that recovery, so a new empty lane cannot be reset while its rotation pointer is still reaching the read model.
- Locally authored rotations retain their target index until the read model observes that index or a newer one. Owner derivation and snapshot adoption both honor the pending target, so an older snapshot cannot roll back the write lane or its cooldown while the pointer write propagates.
- Owner rotations are now pointer-only for contacts, cashu, messages, and transactions; historical lanes stay visible for reads instead of being pruned or copy-forwarded, and cashu duplicate prevention now guards new inserts by token/raw-token identity instead of mirroring rows into a legacy lane
- Contacts are capped per active contacts owner at `MAX_CONTACTS_PER_OWNER` (currently 100); when the active contacts owner fills up, Linky rotates to the next contacts owner while still reading older contacts owners
- Evolu debug views (`#evolu-current-data`, `#evolu-history-data`) scope contacts/history to active owner lanes, with history retaining one previous contacts lane as backup
- Evolu diagnostic row counts subscribe to history mutations only while an Evolu settings page is open and refresh on entry, including rows arriving after account restore. Pending or failed counts display as unknown; a SQLite query failure invalidates the snapshot until reload because Evolu retains its unresolved query promise.
- Evolu server badges count successful socket probes, not completed synchronization. A stored Evolu error no longer marks every reachable relay disconnected; the settings pages show quota failures separately and retain a warning that changes may remain local. Error diagnostics retain only the typed error and public owner link, never token payloads.
- Recovery from an already-rejected owner quota replays the affected device's unchanged history to a relay with enough capacity, either after a quota increase or after adding a capable relay on every device. Normal reload preserves the rejected mutations and spent-token records; rotation cannot shrink the old lane's history. Server settings expose a normal reload/retry, and clearing Evolu data is blocked while a quota error is present. Adding a server never requires wiping local storage. Evolu retains errors even after another relay converges, so a quota warning can persist while the full relay remains enabled; successful socket probes or a dismissed warning are not proof of recovery. Verify the missing data and spent-token records on another device.
- Core app remains local-first/client-side; optional background notifications are handled by the separate `apps/push` Bun service
- Cashu row updates MUST target the row's OWN owner lane, not the active write lane: Evolu materializes rows keyed by `(ownerId, id)`, so `update("cashuProof", {id, state}, {ownerId: activeLane})` silently no-ops on a row that lives in an older `cashu-n` lane (it writes a phantom row in the active lane and leaves the real proof spendable, blocking later payments). The linkshu adapters keep the lane per loaded row and reuse it for every update; inserts go to the active lane, except an upsert of a row that already exists in an older lane, which stays there

### Nostr messaging

- The chat editor handles image files in the browser `paste` event, so keyboard shortcuts and system Paste stage the first image the same way the attachment button does, ignoring accompanying clipboard text/HTML; pastes without images retain plain-text insertion at the caret. Staged attachments are app-level state next to the text draft (the `chatAttachments` list in `useContactsMessagingComposition`; the file input is `multiple` and a paste stages every image in the clipboard), validated on staging so oversized or unsupported files are refused with a status instead of at send time, and they survive navigation like the text draft. The send button ships each attachment as its own image message in order (the first one carrying and consuming the active reply context) and the text draft as a separate message after them, because the private-image payload has no caption field. A file leaves the list only after its send was handed off, so a failure keeps it and everything after it staged for retry. Edit mode neither stages nor sends attachments.
- Both full-screen attachment viewers (image and PDF) are portaled to `<body>` for the same reason as the message actions sheet: on iOS the chat scroller is a composited layer whose stacking context paints a `position: fixed` overlay below the topbar and the compose bar. The image viewer zooms through `hooks/useImageZoom` (pinch and one-finger pan via pointer events with `touch-action: none` on the stage, double-tap to toggle 2.5×, trackpad/wheel zoom through a non-passive listener because React's `onWheel` cannot cancel page scroll); a gesture that moved swallows the trailing click so a pan never closes the viewer.
- The whole receive side flows through linkstr's `WrapInbox`: `useLinkstrInboxSync` registers the app's one wrap-inbox handler and exposes the same typed dispatcher to the notification-open composition — chat messages and own-message confirmations apply through `chatInbox.ts`, reactions through `reactionInbox.ts` (unresolved reactions stay queued until their referenced message arrives), payment notices and bank-offer snapshots through `inboxNotifications.ts`. Notification taps call linkstr's one-shot `fetchWrapEvent` with push relay hints and dispatch the result as backfill before opening the typed event's peer conversation. App-side policy (blocked pubkeys, custom-identity `since` cutoff, known-contact vs `unknown:<pubkeyHex>` conversation resolution) stays in the dispatcher; interruptions (toasts, PWA notifications) fire only for `delivery === "live"` events. Contact-suggestion discovery (`useContactSuggestions`) starts when the add-contact route and linkstr read relays are ready, independently of search input, and goes through linkstr's `Profiles.discoverActiveProfiles` (two-stage recent-activity scan + kind-0 lookup over the configured read relays; product filtering stays app-side). The app scans only kind-30315 statuses (`activityKinds: [30315]`, `authorScanLimit: 200`) because the default activity kinds are saturated by the public relays' global kind-1 traffic within hours, which left the `@linky.fit` suggestion list permanently empty; statuses are the kind linky itself publishes, so they are the discriminating activity signal. Because the scan sees only statuses, onboarding publishes an empty `d=general` status right after the initial kind-0 profile (`publishNewProfileMetadata`) — without it a fresh account has no activity event and never appears in the suggestions; that status publish is best-effort and never aborts account creation. The list is presented as "new Linky users", so the scan window is one hour (`activeWindowSeconds: 3600`) and the newest three `@linky.fit` profiles by last status are pinned to the bottom of the search step; the section is hidden as soon as the search field has any text. A profile counts as a Linky user by its raw `lud16`/`lud06` suffix, before the synthetic `npub…@linky.fit` address is hidden for display — fresh accounts have only that address, so stripping it first would filter out exactly the new users the section is for. Add-contact search (`searchNewContact` in `useContactEditor`) runs two lookups concurrently and reports progress to the page every time either one learns something, so the list renders before the slower lookup settles and shows up to `CONTACT_SEARCH_RESULT_LIMIT = 6` candidates. Exact resolution (npub decode or NIP-05 lookup with a 3s abort, including bare `@linky.fit` names) yields one candidate flagged `isExactMatch` (rendered green, always first); it is surfaced immediately from the identifier plus any cached profile and its kind-0 metadata is filled in when the profile fetch lands — the final result waits for that fetch at most 3s. Text search goes through linkstr's `Profiles.searchProfiles`, which sends the NIP-50 kind-0 `search` filter only to `NOSTR_SEARCH_RELAYS` (`VITE_NOSTR_SEARCH_RELAYS`, default `wss://search.nos.today` + `wss://nostr.wine`; the read relays are strfry-based, do not implement NIP-50, and are used only as a fallback when no search relay is configured — `relay.nostr.band` was unreachable when this was verified in August 2026). Each relay gets the query twice — as typed and with a trailing `*` (`prefixSearchQuery`, skipped for words under three characters or queries that already use `*`/quotes) — because the search relays' full-text indexes match whole words, so "chaincamp" alone never returned "chaincampcz"; relays that take `*` literally answer the companion with nothing. Each relay answer is ranked as it arrives (`onHits`) and relays still silent at the 2.5s deadline are interrupted rather than awaited. Hits are re-checked locally with an accent-insensitive per-word match over name/display name/NIP-05/lud16/about (a guard against relays that ignore `search`), then ranked: profiles whose raw `nip05`/`lud16` ends in a `preferredDomains` entry (the app passes `linky.fit`) come before everything else, then name tier (exact name, prefix, every word in a name, elsewhere), with the relay's own result order as the within-tier signal nudged by nip05/picture presence and by agreement between relays; text-search hits are never marked exact even when their self-declared `nip05` equals the query, because only the NIP-05 lookup verifies it. Payment telemetry publishes through linkstr's `PaymentTelemetry` with a fresh ephemeral key per send and no push marker, enqueued as durable `Outbox` jobs. With the service worker on the headless runner, the app has no direct `nostr-tools` relay I/O left — linkstr is its single Nostr surface
- The inbox cursor persists per pubkey in localStorage (`linky.inbox_cursor.<pubkey>`) through the `InboxCursorStore` layer that `useLinkstrConfigSync` builds into the linkstr runtime; the handler in `useLinkstrInboxSync` only passes a now − 3 days `since` fallback for a first session with an empty store. `WrapInbox` widens `since` by the 2-day NIP-59 backdate margin itself, so every session replays a bounded window that row-level dedupe (by rumor id — linkstr events carry no wrap ids, so incoming rows store the rumor id in the `wrapId` column) absorbs; the replay is also what restores in-memory bank-offer state after a reload (own-offer self copies arrive as `OwnBankOfferSnapshotConfirmed` with `to` — the non-author p-tag — mirroring the chat/reaction own-echo split, so the conversation resolves even though the local user is both author and offerer)
- Edited chat rows keep the original message's rumor id on both peers, including after enqueue and delivery acknowledgement. The edit receipt's `rumorId` identifies the edit event; its `editOf` identifies the message used by reactions, replies, and later edits.
- `OwnChatMessageConfirmed` is reconcile-only by design: same-identity devices share Evolu (issue #249 invariant), so the sending device's Evolu write is the sole cross-device propagation path for own messages. The echo only flips a matching pending row (by clientId, else rumor id) to `sent` and fills its rumor id; an echo with no matching row is dropped, never appended — the legacy append-fallback for outgoing copies is intentionally gone

The contact row stays the single display source of truth: `name`/`lnAddress` always hold the effective value, and every UI reads the row, never the profile cache. While a flag is unset the field follows the profile via `syncContactsFromProfile`, which updates on newer watch events but clears a field only when the *previous* cached profile provided exactly the row's current value — a value the profile never supplied (legacy manual entries, search fallbacks like a NIP-05-derived lightning address) is never destroyed. The contact editor (`useContactEditor` + `app/lib/contactProfile.ts`) seeds fields with the local override only; the public value appears as placeholder and as a hint under an overriding field. Contact rows are never rewritten by profile sync while the contact form routes are open, and the edit form seeds once per contact id so row/profile updates cannot wipe in-progress typing

- Bank-offer snapshot rows (`bank-payment-offer:<contact>:<offer>`, one merged row per contact and offer) carry the snapshot's rumor id as `rumorId` on both the sending and receiving side. This is what lets a payment-confirmation image, sent as a reply to the `bank_paid` snapshot, be correlated with the offer by the *offerer* (who has to decide whether to release the sats), not just previewed locally by the payer
- Chat attachments (kind 15 file messages) are one wire shape for images and PDFs: the file is AES-GCM encrypted client-side, uploaded base64url-encoded to Blossom, and the rumor carries the key/nonce/hashes in tags. Images are re-encoded to JPEG (≤2 MB) and carry a `dim` tag; PDFs (≤2 MB, checked before upload with a localized rejection) are sent byte-for-byte with no `dim` and a `name` tag holding the original file name — `PrivateImage.width/height/fileName` are optional for this reason, and the app's compact `linky:image:v1:` content mirrors it (`w`/`h`/`f`). The receiver renders by `fileType`: images inline; PDFs show the first page rasterized by pdf.js (`pdfjs-dist`, dynamically imported into its own `pdfjs` chunk and excluded from the service-worker precache so non-PDF users never download it) and open into the same full-screen viewer as images, where save/share live. PDF bubbles decrypt only near the viewport (like images), the download is capped before buffering (declared `encryptedSize` and the actual body), decrypted PDF bytes must start with the `%PDF-` magic, rasterization has a per-page pixel budget, and the peer-supplied file name is sanitized to a plain basename with a forced `.pdf` extension on save/share. A PDF that fails to rasterize falls back to a plain file card. Cross-version: clients that predate this release drop an incoming PDF on the wire path — their linkstr codec requires `dim`, so the wrap ends as `WrapDropped` (`invalid-image`) and nothing is shown; only a same-identity device receiving the row over Evolu sync shows it as raw `linky:image:v1:` content. No fallback text rumor is sent, to avoid duplicate messages on current clients
- Only decrypted inner rumor content from `kind: 1059` gift wraps is persisted; linkstr's chat codec rejects nested NIP-44 ciphertext when it decrypts against the sender/tagged peer or the outer wrap pubkey so outer payload blobs are not shown as messages
- Linky publishes both NIP-65 relay metadata (`kind:10002` with `r` tags) and NIP-17 DM inbox relays (`kind:10050` with `relay` tags) from the user's configured relay list via linkstr's `RelayLists` (one operation, per-event receipts) so external clients can discover where to deliver gift-wrapped DMs; `useRelayDomain` fetches the own lists through `fetchOwnRelayListsAtom` on login (each relay's fetch bounded at 8s so a silent relay can't hold discovery) and republishes the last known list when no remote list exists (defaults for a fresh identity). The discovered list is cached per pubkey in localStorage (`linky.nostr_relays.v1.<pubkey>`) as a startup bootstrap: a cold launch connects straight to the last known relay set and the background fetch only rebuilds the linkstr runtime when the list actually changed; the signed events stay authoritative, with cached `relaysUpdatedAt`/`dmRelaysUpdatedAt` timestamps guarding against a relay serving a stale list. Publishes go to the same relay set the app reads from (write relays are no longer pinned to the defaults; the defaults are always merged into the read/write set as bootstrap relays)
- The relay upgrade silently adds `wss://nostr.linky.fit` to each identity's startup list and republishes both Nostr lists with Linky included. It preserves the newer cached list when fetched events are stale; otherwise it keeps the endpoints from both fetched lists. Completion (`linky.nostr_relays.linkyRelayAdded.v1.<pubkey>`) is saved only after both publishes succeed and the updated cache is readable. Failures retry after 30s, on reconnect, or next launch. Later user edits are respected. `VITE_NOSTR_RELAYS` overrides skip this migration; production defaults include Linky as a bootstrap relay. The inspector records completion with links to both signed events.
- linkstr's wrap authentication also rejects malformed inner events that reuse the outer gift-wrap pubkey, preventing random wrapper keys from surfacing as unknown-message ciphertext threads
- Unknown-chat warning panel supports `Add contact` (creates a real contact with the best available Nostr name, while the localized `[Unknown]` / `[Neznámý]` prefix stays UI-only until the contact is saved, migrates existing unknown-thread messages to the new contact id, keeps user in the same chat) and `Block` (confirms, adds pubkey to `linky.blocked_nostr_pubkeys.v1`, publishes a Nostr mute list `kind:10000` with the merged blocked `p` tags when the user has an active `nsec`, removes the local unknown thread immediately, and future inbox sync ignores the blocked pubkey); the mute list goes out fire-and-forget through linkstr's `publishMuteListAtom`
- Profile now publishes the small exchange-currency status as NIP-38 `kind:30315` with `d=general`, storing the checked `BTC`, `CZK`, `USD` list as the status content, the contacts list renders fetched statuses in small italic text next to names, and the contact filter bar exposes parsed status currencies like `CZK` as quick filters
- Chat now supports Cashu payment requests: the composer shows a `Request` action next to `Pay`, request messages are sent as NUT-18 `creqA...` payloads over the existing NIP-17 DM flow, and request cards render `Requested` / `Paid` / `Declined` status with in-chat `Pay` and `Decline` actions
- Bank payment offer (proxy payment) SPD payloads persist in per-offer localStorage keys (`linky.bank_payment_offer_spd.v1.<offerId>`, offerer-pubkey scoped, 1-hour self-cleaning expiry) so offers survive app reload on the creating device; the auto-responder sends `bank_details_sent` to exactly one winning recipient guarded by a per-offer lease lock plus a persisted sent marker, publishes the contact wrap before the self copy so a partial publish cannot fake a sent state, and only `canceled`/`settled` (not a single recipient's `declined`) end the whole offer for payload cleanup and inbox-sync suppression; the auto-responder also retries every 30 s while a non-expired `accepted` entry still awaits bank details, so one failed publish no longer strands the acceptor; cross-device offer sync is tracked in issue #202
- Bank payment offers can be staggered: the SPD page keeps recipient selection ordered (numbered avatars; re-adding a removed contact appends it to the end) and takes a delay of 0–30 s. With a delay, only the first recipient gets the offer at once; the rest persist in `linky.bank_payment_offer_stagger.v1.<offerId>` (offerer-pubkey scoped) with per-recipient due times, and a dispatcher effect in `useBankPaymentOffers` sends each one when due (surviving app reload), guarded by a per-offer lease lock against concurrent tabs and retrying failed publishes every 5 s. Delayed sends carry an explicit `expiresAtSec` = first send + 5 min so extending the offer never extends its total lifetime; earlier recipients can still accept after later ones join. The queue is discarded once any recipient reaches a status other than `offered`/`declined` (a winner exists or the offer ended) or once it expires. The offerer's detail page lists recipients still waiting in the queue (read from the same record) with a "Queued" status chip. The last used delay and recipient count persist (`linky.bank_payment_offer_stagger_delay_sec.v1`, `linky.bank_payment_offer_recipient_count.v1`) when an offer is sent and prefill the next proxy payment; neither is a settings-page option
- Scanned bank payment fields (amount, recipient, account, BIC, reference, variable/specific/constant symbol, message, due date) can be edited on the SPD page before the offer is sent. Editing is a route state (`#wallet/bank-payment/<payload>/edit`) entered from the topbar pencil, so the topbar/hardware back button leaves the form and discards the draft; the form itself only has Confirm. While editing, the request button, recipient chips and stagger stepper are hidden. Edits stay in page state until the request; `updateBankPaymentFields` validates the account (IBAN mod-97, or a Czech/Slovak `prefix-number/bank` account with mod-11 checks that is converted to an IBAN of the scanned IBAN's country) and BIC, re-encodes the payment in its original format (SPD, EPC, PAY by square) and re-parses it, so the recipient receives a QR their bank app can read. CZ/SK IBANs are displayed and edited in domestic notation (`utils/bankAccount.ts`). The SPD parser splits `ACC:IBAN+BIC` into `ACC` and `BIC` fields and the serializer joins them back. The currency is not editable because it selects which contacts are offered the payment; an SPD `CRC32` field is dropped on edit because it authenticates the original string
- Payment result logging in `useOwnerScopedStorage` now also queues anonymous payment telemetry in owner-scoped localStorage; `useAnonymousPaymentTelemetry` hands that buffer to linkstr's `Outbox` (one job per event, ref `telemetry:<id>`), which owns delivery and retries from then on, so the app keeps no retry state of its own. The buffer exists only because events are recorded before the linkstr runtime is necessarily ready, and the lease lock now guards the enqueue step alone — the outbox cannot dedupe the same pending item across tabs. Terminal telemetry results are acked and dropped by the global results listener; delivery still uses a one-off ephemeral sender key per attempt inside `PaymentTelemetry`
- Chat retention is enforced in `useMessagesDomain` (latest 500 messages/contact, 3000 global; reactions capped to 5000 and orphaned reactions are pruned)
- The contact-list unread dot is derived, not event-driven: each contact row carries a synced `chatLastSeenAtSec` read cursor, and a conversation is unread when its newest incoming message is newer than the cursor (`app/lib/chatUnread.ts`; a missing cursor — pre-upgrade rows and unknown-contact threads, which have no row to persist to — falls back to "unread iff the last word is theirs"). `useChatReadCursorSync` advances the cursor while a chat is open in a visible tab (`document.visibilityState === "visible"` — a backgrounded tab does not mark as read) to the newest displayed message's `createdAtSec` (message time, never `Date.now()`, so sender clock skew cannot strand chats unread or mark undisplayed messages read), writing through the contact's owner lane only when the conversation is unread and the target exceeds the stored cursor (owner lanes rotate on write count). Toasts and OS/PWA notifications stay live-event driven in `useLinkstrInboxSync` and are unrelated to the dot
- Read receipts ("seen") are cursor-based on both sides — deliberately no per-message columns, because a receipt covering N messages would otherwise cost N row writes across rotating message owner lanes. The peer's latest reported window persists as `contact.chatPeerSeenSinceSec`/`chatPeerSeenAtSec` (one sparse contact-lane write per receipt that actually advances; monotonic by `seenUpToSec` so the 2-day inbox replay is a zero-write no-op; `seenUpToSec` clamped to now + 1 day against hostile future cursors; receipts from blocked or unknown senders dropped — unknown threads have no contact row). Outgoing bubbles with `createdAtSec` inside the window render a seen check; absence renders nothing, because absence is ambiguous (peer may have receipts off). Sending is gated by the "Send read receipts" toggle, enabled by default: an absent storage key self-initializes the baseline (`linky.seen_receipts_enabled_at_sec.v1`) to the first launch that has the feature, so fresh and updated installs alike start sending receipts while anything older than the baseline is never reported — pre-feature/pre-enable history behaves on both sides as if receipts were off. Turning the toggle off persists an explicit `"0"` (key removal would re-enable on next launch); re-enabling records a fresh baseline. `useChatSeenReceiptSync` sends while the chat route is open in a visible tab, targeting the newest displayed message time (never wall clock) and firing at most once per incoming batch; "already reported up to" lives in a session map seeded by the receipts' own self-copy echoes that the bounded inbox replay restores every session — cross-device and cross-session resend dedupe with zero persistent state. A failed send rolls the map back so any later trigger retries with a superseding receipt

### Wallet and payments

- Wallet receive (`#wallet/topup`) keeps the amount-entry invoice flow, now also exposes secondary `No amount`, `Paste`, and `Scan` actions at the bottom, and `#wallet/topup/no-amount` renders a reusable QR from the user's lightning address for amount-less LNURL-pay receipts
- Display-unit preferences now live on the dedicated `#settings` page reached from the menu `Jednotky` row; users toggle which currencies are allowed there, defaulting to language currency plus `sat`, can also enable a hidden `*****` unit that masks amounts across the app, and wallet balance / amount-entry displays cycle through the allowed currencies on tap
- Outgoing Cashu payments select a single mint that can cover the payment amount; Linky does not split one payment across token balances from multiple mints
- Token list (`#wallet/tokens`) offers a `Melt to [main mint]` action beneath the available proofs; it picks the non-main mint with the largest accepted-token balance, pays a fresh top-up quote on the selected main mint with those tokens, retries with slightly lower amounts when melt fees require it, and stores any source-mint remainder plus the newly minted main-mint token back into Evolu
- Changing the selected main mint never moves existing balances: no confirmation dialog, no automatic swap. Funds move to the main mint only when the user explicitly asks — the `Melt to [main mint]` action on the tokens page or the payment-mint-melt confirmation during a payment (the `cashuAutoswap` Advanced setting and its automatic post-receive sweep are removed)
- Cashu token detail (one transfer) uses the receive-invoice style card, shows the token amount above a larger centered QR, and hides the raw token string
- Wallet token flow is split into a main `#wallet/tokens` page plus dedicated `#wallet/token/new` import and `#wallet/token/emit` issuance pages; the main page lists proofs by stored state and open transfers separately, and handed-out/externalized/held proofs stay out of the spendable balance
- Wallet now also exposes a small `Transakce` / `Transactions` link from `#wallet` to a dedicated `#wallet/transactions` page that lists all known Evolu-backed payment history rows
- Transaction history merges an emitted Cashu token row into the later successful payment row when that exact issued token is subsequently spent, so emit-then-send appears as one history item
- **Animated QR (NUT-16).** A cashu token that exceeds what one QR can carry is shown as a multi-part UR animation (`ur:bytes`, Blockchain Commons) instead of no QR at all, which is what the token page used to fall back to. A single static code is still preferred up to QR version 20 (`STATIC_QR_MAX_VERSION`, 97×97 modules), because it can be photographed, shared as an image, and read by wallets without NUT-16; past that a phone camera no longer reads the code off another phone's screen even though a version-40 symbol would still hold the data, so the animation takes over there rather than at the capacity limit. The token page offers an animation toggle for larger tokens. Turning it off renders the full token as one static QR up to version 40; tokens beyond that capacity show a message to re-enable animation or copy/share instead of displaying an incomplete frame. The choice stays local to the token page. Frames are uppercased so the encoder can use its denser alphanumeric mode, and the encoder keeps handing out fountain parts rather than looping a fixed sequence, so a receiver that joins mid-cycle or misses a frame still finishes. The UR library is the cashu fork NUT-16 names (`@gandlaf21/bc-ur`), imported by its ESM path because the CJS entry requires the ESM-only `cborg`; its CBOR encoder recognises bytes by `instanceof Uint8Array`, so the payload is copied into this realm's `Uint8Array` before encoding, otherwise a polyfilled `Buffer` is encoded as a map of numeric keys that roughly doubles the frame count and decodes back as a plain object. On the reading side a frame is not a payload — `useGuideScannerDomain` collects frames and keeps the camera running until the animation completes. The Android shell's native preview already streams every decoded code, so its frames go through the same collector and the native scanner is stopped only once the payload is complete; the shared web progress bar sits in the scanner footer, outside the native preview. The preview viewport follows header/footer size changes and window resizes so progress and actions stay visible. The iOS one-shot scanner and the photo picker say a frame is not a payload instead of failing silently, because neither can ever collect a second frame
- Lightning pay scan supports lightning addresses plus LNURL-pay bech32 / `lnurlp://` / HTTPS targets; LNURL-withdraw (`lnurlw`) QR scans now show the withdrawable sats for confirmation and then pull the amount into the wallet via the selected mint top-up flow; unknown recipients open the same amount-entry UI as contact pay, but without avatar/name until matched to a saved contact
- LNURL-auth (`lnurl1…`, `keyauth://`, or a plain HTTPS target) carries `tag=login` and the challenge in the scanned URL itself, so `useScannedTextHandler` recognizes a login **before** the LNURL-withdraw probe fetches the same target — the greedy withdraw/pay resolvers accept any HTTP URL and would otherwise claim it. It is allowed from every scan entry point, including `receive`, because it moves no money. The user approves a sheet naming the domain; only then is a key derived and the callback called. Nothing is persisted: the session belongs to the domain, and Linky keeps no record of where the user is logged in
- All three LNURL sub-protocols live in `@linky/linkshu` (`lnurl/common.ts` holds bech32 decoding, http-target normalization, the `{ status, reason }` envelope, and the optional `LnurlFallback` retry), so the web app keeps only the wrappers that supply the `/api/lnurlp` CORS fallback. `submitLnurlAuth` takes a `sign` callback instead of a key, which keeps the wallet package free of key material — `apps/web-app/src/lnurlAuth.ts` is what binds it to `@linky/identity`. LNURL-auth requires an explicit `status: "OK"` rather than treating a non-error response as success, so a login the domain never confirmed is not reported as done
- Cashu mint quote/check/mint calls go directly to the selected mint with CORS fetch options and do not pass quote ids or proofs through a Linky proxy (the dev Vite `/api/lnurlp` proxy exists only for LNURL-pay CORS workarounds)
- Cashu topup quote creation and claim talk to the mint directly (via linkshu on web and native), so Linky servers never see top-up quote ids or minted proofs
- Interrupted top-ups persist as linkshu `topup` operations (in the synced `OperationStore`, including the invoice text and the reserved counter slot) and resume via `Topup.resumePending` on any device; a record is retired only when the mint itself confirms the quote unpaid and expired, never on local age alone
- Cashu tokens written to NFC remain listed as greyed `externalized` transfers, their proofs are excluded from available balance and outgoing payments, and return-to-wallet re-accepts them into fresh spendable proofs; token detail also offers Share for the same `cashu://cashu...` deeplink used by NFC writes
- Wallet/contact QR scanning now keeps fallback actions available when camera permission is denied/unavailable

- QR scanning uses the shared `ScanModal` controls with a native ZXing preview on Android when available, falling back to `getUserMedia` on the web. Both streaming paths collect animated QR frames until the payload is complete.
- Android native shells also register `nostr://` and `cashu://` custom URI schemes and forward incoming URLs through `LinkyNativeDeepLinks`; the current handler accepts contact `npub` links plus Cashu token links, reuses the scanned-text add/import flows, opens the saved contact detail, and imports tokens into the wallet
- Android native shells also accept NFC NDEF tags for the same flows: `ACTION_NDEF_DISCOVERED` URI records with `nostr://` / `cashu://` and `text/plain` NDEF records whose payload starts with those schemes are normalized in `MainActivity` and forwarded through the same deep-link bridge
- Android native shells also expose NFC writing through `LinkyNativeNfc`; token detail writes `cashu://cashu...` and profile writes `nostr://npub...` as NDEF URI records, with web-app UI hidden when the native bridge is unavailable
- Native scan/notification injected bridge methods must be invoked as bridge methods (`bridge.method()`), not detached function references, otherwise Android WebView rejects them as non-injected calls

## Push service (`apps/push/`)

- Push service env is documented in `apps/push/.env.example`; `PUSH_VAPID_SUBJECT`, `PUSH_VAPID_PUBLIC_KEY`, and `PUSH_VAPID_PRIVATE_KEY` must be set before `apps/push` starts
- `apps/push` CORS allowlist is configured via `PUSH_CORS_ORIGIN`; it accepts `*` or a comma-separated list of allowed web app origins
- Push service proof events use `kind: 27235` with short-lived per-pubkey challenge nonces; `/subscribe` and `/unsubscribe` both require valid proofs per affected pubkey, full unsubscribe only happens when the last proven pubkey is removed, the server never decrypts NIP-17 payloads, and it only emits generic notifications for outer `kind: 1059` events tagged `["linky","push"]`, so sender self-copies / reactions / edits can sync over relays without triggering push
- `apps/push` relay watcher defaults now match the web app chat publish relays (`wss://relay.damus.io`, `wss://nos.lol`, `wss://relay.0xchat.com`) unless overridden via `PUSH_DEFAULT_RELAYS`
- `apps/push` relay watcher uses a rolling 3-day catch-up `since` window to accommodate NIP-59 randomized outer `created_at`. PushInbox keeps a FIFO set for live-emission dedupe and bounds each relay subscription attempt to 10 minutes before reconnecting with a fresh window, which recovers relays that drop a REQ without closing the socket. The service suppresses each relay's backfill through EOSE, records only wraps it attempts to deliver in its restart-safe SQLite seen ledger, and prunes rows after the 3-day lookback plus a 6-hour margin; there is no dedupe-TTL env knob. Linkstr stays console-free and reports through callbacks; `apps/push` logs invalid push-marked wraps with a `failure=` tag, per-relay EOSE catch-up, relay attempt endings with reasons, and fatal watcher failures
- Container publishing is handled by `.github/workflows/push-image.yml`, which builds `apps/push/Dockerfile` and publishes the image to GHCR

The contenteditable chat editor uses the same pill classes for its DOM-managed entities.
