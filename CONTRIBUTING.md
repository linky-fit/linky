# Contributing

Thanks for wanting to help with Linky. Here is how to get a change merged without wasting your time or ours.

## Open an issue first

Open an issue before you write code when:

- the change is a product decision: a new feature, a changed flow, different copy or behavior users will notice
- the change is large, or touches sync, storage, the protocols or the packages
- you aren't sure the change is wanted

Wait until a maintainer agrees with the direction. A PR for a feature nobody discussed will likely be closed, however good the code is.

A bug fix with an obvious cause can go straight to a PR. Link the issue if one exists.

If you found a problem but don't want to fix it, an issue is a real contribution. Describe what you did, what you expected and what happened instead. Your English doesn't need to be perfect. A short issue in rough English helps us more than a polished PR we have to decode.

## AI tools

Use whatever tools you like, but you are the author of the PR:

- understand what your change does and why. You don't have to read every generated line, but you have to be able to explain the change when we ask
- write at least a short description of the change yourself, in your own words. Grammar mistakes are fine!
- an agent can write the description and your comments, but mark those parts as generated, for example with `> Generated by <agent>` above them
- drop the changes you didn't mean to make

PRs that are just AI slop get closed. That means generated code the author doesn't understand, wrapped in a generated description nobody checked. Reviewing those costs us more than writing the fix ourselves. If you can't explain the scope of a change, an issue helps us more.

## Before you open a PR

1. Set up the project as described in the [README](./README.md#development).
2. Run `bun run check-code` and `bun run test` until both pass. If you changed a flow the Playwright tests cover, run those too.
3. Run the app with `bun run dev` and try your change the way a user would. Passing tests aren't enough. Check it at phone width, Linky is mobile-first.
4. Keep the PR small and to one change. Refactors or formatting of unrelated code go in a separate PR. If you still want to add multiple unrelated changes into one PR, separate them into well scoped commits.

Working on a package under `packages/`? Its guide in `packages/<name>/docs/` explains how the package is meant to be used.

## The PR description

If we have to guess what changed, we are much less likely to review it.

Tell us what changed and why the change should exist.

If the PR makes anything resembling a UI change, include clear before and after screenshots. If the change depends on motion, timing, transitions or interaction details, include a short video.

If you change the exported API or documented behavior of `@linky-fit/linkshu` or `@linky-fit/linkstr`, state the proposed SemVer effect (patch, minor or breaking). Leave `version` alone; the bump happens at release ([`docs/npm-releases.md`](./docs/npm-releases.md)).

Paste this checklist into the description and tick the boxes:

```markdown
- [ ] I ran the app and tried this change myself
- [ ] Before and after screenshots (or a video) are attached, or the UI didn't change
- [ ] I understand why this change is needed, what this change does and can explain it
```
